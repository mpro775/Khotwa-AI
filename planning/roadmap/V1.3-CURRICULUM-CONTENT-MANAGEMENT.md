# V1.3 — إدارة المناهج والمحتوى للمعلم

**اسم المهمة للوكيل:** `DEV-03 — Teacher Content Studio`  
**الهدف:** المعلم يستطيع إضافة درس ومهارات ومسائل وتلميحات وعلاج، ومراجعتها ونشر نسخة آمنة من المحتوى دون تعديل الشيفرة.

## 1. تجربة المستخدم المستهدفة

يدخل المعلم المصرح له إلى لوحة محتوى عربية، ينشئ وحدة «المعادلات الخطية»، ويضيف درسًا ومهارة وسؤالًا مع حل مرجعي. يختبر السؤال على محرك الرياضيات، ثم يحفظه **مسودة**، ويراجعه وينشره. تظهر المسألة للطلاب الجدد دون تغيير محاولات الطلاب الذين يستخدمون إصدارًا قديمًا.

## 2. اعتمد على الموجود

- جداول `content_releases`, `skills`, `skill_prerequisites`, `problems`, `problem_revisions`, `problem_skills`, `intervention_templates`, `content_pairings`.
- العقود العامة في `docs/12-API-CONTRACT.yaml`، وخدمات NestJS `business.ts`, `tutoring.ts`, `learning.ts` والمحرر العربي في React.
- أدوار المستخدم من V1.2؛ إذا لم تُنفذ V1.2 بعد فلا تنشئ نظام دخول مستقل للمعلمين.
- محرك SymPy يدقق الحل، وGemini يمكن أن يقترح صياغة فقط بعد موافقة/مراجعة، ولا ينشر تلقائيًا.

## 3. المهام

### DEV-031 — هيكلة محتوى بسيطة

أضف عند الحاجة `subjects`, `units`, `lessons` وروابطها بالمحتوى الحالي، أو حقولًا منظمة إذا كفى ذلك. اجعل التسلسل:

`المادة → الوحدة → الدرس → المهارات → مسائل/علاج/نقل`.

احتفظ برموز وإصدارات ثابتة لكل عنصر، ولا تكسر علاقة محاولة الطالب بإصدار المسألة.

### DEV-032 — دورة نشر واضحة

استخدم حالات: `draft → in_review → approved → published → archived`.

- الإنشاء والتحرير على **نسخة draft** فقط.
- تعديل مسألة منشورة ينتج **problem_revision جديدة**؛ لا تغيير سجل مستخدم سابقًا.
- توثيق من راجع ومن نشر ومتى، وبصمة محتوى مختصرة.
- ابدأ بتصاريح `teacher/editor` و`admin/publisher` فقط؛ في الفريق الصغير يمكن للشخص نفسه امتلاك الدورين إذا كان ذلك مصرحًا به.

### DEV-033 — لوحة المحتوى React

صفحات عملية لا تحتاج لوحة ضخمة:

1. قائمة الوحدات والدروس والمهارات.
2. قائمة المسائل مع بحث وتصفية حسب المهارة والحالة والصعوبة.
3. نموذج إنشاء/تعديل مسألة باللغة العربية ومحرر معادلة ومعاينة.
4. شاشة مراجعة «فرق النسختين» وحالة الاعتماد.
5. صفحة نشر إصدار المحتوى والتراجع عنه بنشر إصدار أقدم مؤهل، دون حذف بيانات الطلاب.

### DEV-034 — تحقق صحة المسألة قبل النشر

- تحقق من الحقول، والرموز المدعومة، وصحة مفتاح الحل/مجموعات الحلول عبر SymPy.
- امنع نشر سؤال غير مدعوم أو جواب متعارض مع التحقق الرياضي.
- إذا كانت المسألة علاجية/نقلًا، راجع وجود ربط صحيح بالمهارة والعائلة وصعوبة ملائمة.
- افصل الرسالة التعليمية عن نتيجة الحساب؛ لا تمنح Gemini صلاحية حكم نهائي أو نشر.

### DEV-035 — بنك التلميحات والمراجعة

- واجهة لإنشاء H1–H4 وربط التلميحات بالمهارة/الخطأ، مع معاينة مقدار كشف الإجابة.
- إظهار المصدر: يدوي/مقترح AI، وحالة المراجعة.
- منع إضافة تلميح غير مراجع إلى fallback المنشور.
- حفظ النسخ القديمة المستخدمة في محاولات سابقة.

### DEV-036 — استيراد وتصدير بسيط

- دعم استيراد JSON أولًا، وCSV إذا كان سهلًا ضمن الهيكل الحالي.
- وضع `preview/dry-run`: عدد السجلات المقبولة والرافضة وأسباب الرفض قبل إنشاء السجلات.
- تصدير نسخة المحتوى بصيغة JSON مع رموز المهارات والإصدارات، دون بيانات الطلاب.

### DEV-037 — APIs والصلاحيات

- CRUD للـdraft، مراجعة ونشر وتراجع؛ حدّث OpenAPI والأنواع في React وفق مسار المشروع.
- رفض القراءة/التعديل/النشر دون الدور المناسب.
- الطالب يرى النسخ المنشورة فقط، والمعلم لا يرى محاولات ضيوف أو طلاب حقيقيين ما لم يكن هناك تفويض جديد محدد.

## 4. اختبارات قبول بسيطة

- إنشاء درس + مسألة + حل مرجعي صحيح، ثم نشرهما وظهورهما للطالب.
- رفض نشر مسألة ذات حل خاطئ أو صيغة غير مدعومة.
- تعديل مسألة منشورة ينتج Revision جديدة وتبقى محاولة قديمة مرتبطة بالأصل.
- المعلم المصرح له يحرر draft، وغير المخول لا يستطيع النشر.
- استيراد ملف مختلط يعطي معاينة صحيحة دون إدخال عناصر مرفوضة.
- بقاء التلميحات والمحتوى التعليمي غير المراجع خارج العرض العام.

## 5. النتيجة والتسليم

- واجهة إدارة محتوى حقيقية متصلة بـNestJS/Prisma وتُنشئ نسخًا قابلة للنشر.

- تقرير `qa-reports/DEV-V1.3-DELIVERY.md` مع مثال إنشاء ونشر، وendpoints وmigrations والاختبارات.
