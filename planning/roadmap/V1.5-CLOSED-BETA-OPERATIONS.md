# V1.5 — نسخة Beta محدودة ومراقبة التشغيل

**اسم المهمة للوكيل:** `DEV-05 — Closed Beta Readiness`  
**الهدف:** تشغيل خُطوة لمجموعة صغيرة بإجراءات استقرار وأمان وتكلفة واضحة، دون بنية سحابية معقدة.

## 1. تعريف النجاح

رابط HTTPS لنسخة Beta لا يدخلها إلا المدعوون، ويمكن للمستخدم بدء جلسة وحل مسألة والحصول على تلميح، ويستطيع الفريق معرفة إن حدث خطأ أو بطء أو استهلاك زائد للذكاء الاصطناعي، وإيقاف النسخة أو الرجوع لإصدار سابق بأمان.

## 2. نطاق Beta الافتراضي

- 5–20 مشاركًا بالغًا أو مختبرين داخليين متطوعين أولًا.
- بيانات تعليمية تجريبية/غير حساسة؛ لا توسع لمتعلمين قُصّر قبل إكمال الموافقات والخصوصية اللازمة.
- السيرفر الحالي أو بيئة صغيرة واحدة؛ لا Kubernetes أو بنية متعددة المناطق.
- حسابات الطلاب من V1.2، والمحتوى المنشور من V1.3، وواجهة V1.4.

## 3. مهام التنفيذ

### DEV-051 — إعداد بيئة التجربة

- جهز Compose/إعدادات التشغيل الموجودة أو بيئة نشر صغيرة مماثلة.
- TLS/HTTPS حقيقي، متغيرات بيئة سرية، ضبط Origin/CORS/Cookies.
- لا منافذ عامة لـPostgreSQL أو Python، وحساب DB محدود الصلاحيات.
- ميّز بيئة Beta عن بيانات التطوير وعن إنتاج مستقبلي.

### DEV-052 — الدخول للنسخة التجريبية

- دعوات بسيطة بالبريد أو allowlist من حسابات مختارة، مع إمكانية إيقاف الدعوات.
- وسيلة عملية لسحب الوصول وإبطال الجلسات، لا لوحة إدارة عضويات ضخمة.
- صفحة توضح أنها Beta وطرق إرسال الملاحظات وحدود الخدمة.

### DEV-053 — مراقبة مبسطة

اجمع مؤشرات منخفضة التكلفة:

- عدد الجلسات اليومية والمسائل والتلميحات، دون بيانات شخصية في سجلات التحليل.
- أخطاء 4xx/5xx، وtimeouts لـGemini/Python، وزمن طلبات API p50/p95 عند وجود عينات كافية.
- نسبة fallback وعدد مكالمات Gemini واستهلاك الرموز وتكلفة تقديرية يومية.
- مساحة القرص وحالة PostgreSQL وhealth/readiness.

ابدأ بسجلات JSON منقحة ولوحة بسيطة أو أداة مراقبة موجودة، ولا تنشئ منصة Observability منفصلة ما لم تكن ضرورية.

### DEV-054 — حدود التكلفة والأمان

- حد يومي/شهري اختياري للمصروف على Gemini مع حد للمستخدم وسقف token/output وإيقاف الاستدعاءات عند الحاجة؛ fallback واضح.
- Rate limit للواجهات الحساسة، وفحص الجلسات/CSRF والصلاحيات والتزامن.
- لا تسجل API Key أو OTP أو cookies أو مدخلات طالب حساسة في سجلات الأخطاء.
- أضف كشفًا بسيطًا للتكرار أو إساءة استخدام AI المتكرر.

### DEV-055 — النسخ الاحتياطية والاحتفاظ

- نسخة PostgreSQL احتياطية تلقائية محدودة ومحمية، **مع تجربة استعادة على قاعدة اختبار**.
- تفعيل حذف البيانات وفق السياسة المعتمدة، مع دليل تشغيل وتقرير آخر نجاح.
- خطوات إيقاف وصيانة واستعادة واضحة من README، دون حذف volumes على نحو خاطئ.
- ترقيات قاعدة البيانات عبر migrations موثقة وقابلة للمراجعة؛ لا تشغيل مباشر على بيئة حية دون موافقة.

### DEV-056 — جودة التجربة والتغذية الراجعة

- نموذج Feedback بسيط: نوع المشكلة، رسالة، رقم طلب منقح إن وجد، وإرسال دون أسرار.
- صفحة داخلية صغيرة للمتابعة أو تقرير يومي للأخطاء الأكثر تكرارًا.
- شغّل 5 رحلات E2E أساسية، وفشل Gemini/Python، وخطأ الملكية، واختبار الحذف على staging.
- اجمع ملاحظات المتطوعين وحدد تحسينات V1.6؛ لا تبدأ تطبيقها تلقائيًا.

## 4. قبول المرحلة

- يعمل رابط Beta عبر HTTPS لحسابات مدعوة فقط.
- مسار الطالب الأساسي يعمل، والبديل يشتغل عند عطل Gemini دون فقدان المحاولة.
- سجلات وأرقام أساسية للتكلفة والأخطاء مرئية للفريق، وسقف التكلفة قابل للضبط.
- نسخة DB احتياطية يمكن استعادتها في الاختبار، وحقوق الوصول والحذف مختبرة.
- لا عيب BLOCKER مفتوح يمس تسريب البيانات أو الحكم الرياضي.

## 5. التسليم

- إعدادات نشر Beta ببيانات مثال بلا أسرار، وREADME تشغيل/تراجع/استعادة.
- تقرير `qa-reports/DEV-V1.5-DELIVERY.md`: الرابط/بيئة الاختبار، عدد المختبرين (إن توفر)، المراقبة، الاختبارات، قائمة مشكلات Beta.
- لا تفعّل دفعًا أو تنشر للعامة أو تستخدم بيانات طلاب حقيقية دون موافقة مستقلة.

**بعد V1.5: تُقترح خطة Beta → Product، ثم نبدأ توسعة المواد بمهام منفصلة.**
