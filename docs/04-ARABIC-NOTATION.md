## 0. الغرض وحدود سلطة هذه الوثيقة

تهدف هذه المواصفة إلى جعل **الكتابة الرياضية العربية جزءًا حقيقيًا من بنية خُطوة، لا ترجمة سطحية**. تحدد ما يراه الطالب ويكتبه، وما يُقبل من تنويعاته، وكيف يتحول إلى معنى رياضي موحد، وكيف يُعرض مجددًا دون تغيير المعنى أو اتجاهه.

- هذه الوثيقة **مالكة اصطلاحات اللغة الرياضية، والتطبيع، ومتطلبات الإدخال/العرض**؛ وليست عقد واجهات API أو مواصفة خوارزمية إثبات التكافؤ.
- `10-MATH-ENGINE.md` يملك قواعد التحليل الدلالي والتحقق الرياضي وحدود الثقة؛ و`12-API-CONTRACT.yaml` يملك حقول الطلبات والاستجابات النهائية.
- `05-CURRICULUM.md` يملك اعتماد المنهج والمصطلحات المدرسية التي قد تختلف بين الدول؛ و`15-TEST-AND-ACCEPTANCE.md` يملك عتبات القبول.
- **P0** يعني المطلوب للهاكثون، **P1** تحسينًا مشروطًا، **P2** توسعًا لاحقًا. ظهور مثال من P2 هنا **لا يعني دعمه في نسخة الهاكثون**.
- المرجعية عند الخلاف: المبادئ الثابتة في الرؤية ← المتطلبات المعتمدة في PRD ← النطاق المجمد في MVP ← هذه المواصفة فيما تملكه من اصطلاحات ← عقود التنفيذ. أي تعارض يفتح قرار تغيير، ولا يعالَج بتعديل غير معلن من وكيل.

### 0.1 قاعدة غير قابلة للتفاوض

**النص الذي يكتبه الطالب ≠ التمثيل الرياضي الداخلي ≠ الصيغة التي تظهر له.** يجب الاحتفاظ بها مستقلة ومترابطة. لا يُستنتج معنى عملية من موضع حروفها على الشاشة أو من الترتيب المرئي للرموز بعد تطبيق RTL.

### 0.2 ملف الاصطلاح الأول

- **المعرّف المقترح:** `ar-mashriq-school-v1` — اسم تقني داخلي لملف اصطلاح، وليس معيارًا إقليميًا رسميًا.
- **التجربة الافتراضية المقترحة:** عربية فصحى، أرقام عربية شرقية `٠–٩`، متغير `س`، ومصطلحات مدرسية مشرقية عند اعتمادها تربويًا.
- **اتجاه النص المحيط:** RTL. **اتجاه التعبير الرياضي:** بحسب ملف الاصطلاح ونتيجة الاختبار البصري/الوظيفي؛ لا نستنتجه من اتجاه الصفحة فقط.
- **قيد اعتماد:** اختيار الصف/البلد/المرجع النهائي وإقرار طريقة عرض الصيغ من مختص المادة قبل تجميد `GATE-0`.

## 1. المعجم الإلزامي: ماذا نقصد بالعربية العلمية؟

| المجال | قرار التجربة | النطاق |
|---|---|---|
| الواجهة والشرح | العربية لجميع أزرار الطالب، الأسئلة، الملاحظات، التلميحات، والملخصات | P0 |
| الأعداد المرئية | `٠ ١ ٢ ٣ ٤ ٥ ٦ ٧ ٨ ٩` افتراضيًا | P0 |
| المتغير | `س` لا `x` في مسائل الهاكثون المعروضة | P0 |
| الضرب | `٢س` و`٢(س + ٣)` مع دعم ضرب صريح موثق | P0 |
| المعادلات | صيغة عربية مثل `٢س + ٣ = ٧` | P0 |
| كسور نتائج خطية | `١/٢` نصيًا، وعرض كسر رياضي صحيح عند اجتياز الاختبارات | P0 محدود |
| متغيرات إضافية | `ص`، `ع` بحسب المنهج | P2 |
| الأسس | `س²` | مثال اصطلاح فقط؛ محرك P0 لا يحل الأسس/التربيع |
| مثلثات | `جا` = الجيب، `جتا` = جيب التمام، `ظا` = الظل | P2 |
| الفيزياء | شرح ومصطلح عربي؛ رمز الكمية حسب المنهج؛ وحدات معيارية مثل `kg`، `m/s` كما هي | P2 |
| الكيمياء | أسماء ومفاهيم عربية؛ صيغ عناصر دولية `H₂O`، `NaCl` لا تُعرّب حرفيًا | P2 |
| البرمجة | التعليمات والشروحات بالعربية، والشيفرة واسم المكتبة والكلمة المحجوزة باللغة المطلوبة للأداة | P2 |
| اللغات الأجنبية | شرح عربي عندما يلائم؛ أمثلة المادة بلغتها الأصلية | P2 |

**لا يحق لوكيل AI توليد أسماء عربية لدوال أو كميات من عنده ثم التعامل معها على أنها اصطلاح معتمد.** يُضاف كل مصطلح إلى قاموس مراجَع مع مصدره وملف الاصطلاح الذي ينتمي إليه.

## 2. معيار الأرقام والفواصل والرموز

### 2.1 الأرقام وأنواع المحارف

| المصدر | أمثلة | القرار في P0 | التمثيل الداخلي |
|---|---|---|---|
| العربية الشرقية `U+0660–U+0669` | `٠١٢٣٤٥٦٧٨٩` | **قبول وإظهار افتراضي** | أرقام عشرية عددية 0–9 |
| ASCII `U+0030–U+0039` | `0123456789` | **قبول إدخال** وإظهار عربي موحد | الأعداد نفسها |
| الأرقام العربية-الهندية الشرقية المستخدمة في الفارسية وغيرها `U+06F0–U+06F9` | `۰۱۲۳۴۵۶۷۸۹` | خارج دعم P0؛ يُبلغ المستخدم بعدم الدعم، مع إمكان إضافتها في ملف لاحق | لا تُخمن |
| الإشارة السالبة المعيارية `U+2212` | `−٣` | قبول | سالب أحادي أو طرح بحسب البنية |
| علامة الوصل/الطرح ASCII `U+002D` | `-3` | قبول ثم توحيد العرض إلى `−٣` | نفس العملية |
| الفاصلة العشرية العربية `U+066B` | `٣٫٥` | **غير مدعومة في P0** لأن مدخلات الجبر الأولى صحيحة/كسرية بسيطة | قرار مستقبلي |
| فاصل الآلاف العربي `U+066C` | `١٬٠٠٠` | غير مدعوم في الإدخال الرياضي P0 | قرار مستقبلي |
| النقطة والفاصلة الإنجليزية | `3.5`، `1,000` | خارج P0؛ لا تُفترض فاصلة عشرية أو آلاف | لا يُخمن |
| الفاصلة العربية `U+060C` | `١،٢` | **ليست** فاصلة عشرية في المحلل | غير مقبولة كعدد |
| النسبة المئوية العربية `U+066A` | `٥٠٪` | خارج P0 | P2 |

**مهم:** قبول `2س + 3` لا يعني وجود واجهة ذات متغيرات إنجليزية؛ إنه **تسامح في شكل الأرقام** مع عرض عربي ثابت. ويجب أن يكون توحيد المحارف بلا فقد للمصدر الأصلي.

### 2.2 العلامات الأساسية المدعومة P0

| العلامة | الإدخال المقبول | مثال | المعنى |
|---|---|---|---|
| جمع | `+` | `س + ٢` | جمع |
| طرح / سالب | `−` أو `-` | `س − ٢`، `−٣` | طرح أو سالب وفق الموقع |
| ضرب صريح | `×` أو `*` | `٢ × س` | ضرب |
| ضرب ضمني | التصاق في الحالات المحددة أدناه | `٢س` | ضرب |
| قسمة على ثابت | `÷` أو `/` | `س/٢`، `١/٢` | قسمة ضمن القواعد المدعومة |
| مساواة | `=` | `٢س = ٤` | علاقة مساواة، واحدة في السطر |
| تجميع | `(`، `)` | `٢(س + ٣)` | ترتيب العمليات |
| مسافات | مسافات Unicode المعتادة وفق قواعد المحلل | `٢ س + ٣` | تنسيق لا يغير المعنى في الأنماط المقبولة |

لا ندعم في P0 علامة `^` للأسس، أو `√` للجذور، أو `≤` و`≥` للمتباينات، أو `!` للمضروب، أو `==` للمساواة البرمجية، أو `;` للفصل بين معادلات. إن كان الإدخال مفهومًا لكنه خارج النطاق تكون النتيجة `unsupported`، لا «إجابة خاطئة».

### 2.3 الكسور: قرار محسوم للحد الأدنى، وحدود واضحة

- يقبل P0 **كسرًا عدديًا بسيطًا** ببسط ومقام صحيحين، ومقام غير صفري، مثل `١/٢`؛ يحتاجه الطالب لإدخال ناتج معادلة خطية.
- يمكن قبول `س/٢` و`٢س/٣` عندما تكون القسمة على ثابت معروف غير صفري، ويحدد `10-MATH-ENGINE.md` التحويلات المسموح التحقق منها.
- يعرض الكسر في واجهة الطالب **كبسط فوق مقام** حيث تسمح أداة العرض وتنجح اختبارات RTL؛ ولا تُقلب علاقة البسط والمقام بسبب الاتجاه.
- `١/٢س` **ملتبسة** بين `(١/٢)س` و`١/(٢س)`؛ تُرفض مع طلب أقواس واضحة، ولا تُفسّر تلقائيًا.
- الكسور الجبرية ذات المقام المتغير، مثل `١/س`، **غير مدعومة**؛ الامتناع عن الحكم عليها ضروري لحماية شروط المجال.
- إذا تعذر تحقيق عرض كسر سليم على جميع البيئات المطلوبة، يسجل ذلك كحاجز لـ`GATE-1` وتُختبر صيغة بديلة صريحة لا تغير المعنى؛ لا تُطلق ميزة شكلية مضللة.

## 3. متغيرات وأسماء دوال: لا تخمين في الرمز

### 3.1 المتغيرات

- رمز المتغير الوحيد المدعوم في الجبر P0: **`س`** (`U+0633`).
- `س` ليس كلمة نصية ولا اختصارًا لاتينيًا، ويُنشأ في التمثيل الداخلي **عقدة متغير** مستقلة.
- `ص` و`ع` وغيرهما يصنّفان **غير مدعومين في P0**؛ لا يضمّهما النظام تلقائيًا إلى `س`.
- `x` و`y` وأسماء المتغيرات اللاتينية تُرفض في محرر الجبر العربي P0 برسالة: «استخدم المتغير س في هذا المسار»؛ **لا تحويل صامت من x إلى س**.
- `سَ`، `سـ`، `ﺱ` (تشكيل/تطويل/أشكال عرض Unicode) لا تُعامل باعتبارها س نفسها دون قاعدة معلنة واختبار؛ الأفضل منعها في مدخلات P0 وإظهار طريقة التصحيح.

### 3.2 الدوال المحجوزة للمستقبل

| الاسم العربي المقترح | المعنى | حالة التنفيذ |
|---|---|---|
| `جا` | دالة الجيب | P2؛ محجوزة وليست مدعومة حاليًا |
| `جتا` | دالة جيب التمام | P2؛ محجوزة وليست مدعومة حاليًا |
| `ظا` | دالة الظل | P2؛ محجوزة وليست مدعومة حاليًا |

- الإدخال `جا(٣٠°)` يعيد `unsupported` في الجبر P0؛ **لا يفسره** المحلل على أنه متغيرات عربية مضروبة أو على أنه دالة تم حسابها.
- عند تفعيل الدوال مستقبلًا يلزم تحديد الدرجة مقابل الراديان، ومجال الدالة، وقواعد الأقواس، واصطلاحات المنهج، واختبارات صحة مستقلة.
- `sin` و`cos` و`tan` لا تتحول في واجهة الرياضيات إلى أسماء عربية تلقائيًا ولا تُستخدم لتجاوز عدم دعم الدوال. في **برمجة Python** تبقى أسماء الدوال كما يطلبها API البرمجي.

## 4. الضرب الضمني والأقواس وأولوية العمليات

في P0، أمثلة الإدخال المقبولة ضمن **المعادلات الخطية فقط**:

| الإدخال | المعنى المقصود |
|---|---|
| `٢س` | `٢ × س` |
| `٢ س` | `٢ × س` |
| `٢(س + ٣)` | `٢ × (س + ٣)` |
| `−٣س` | `−٣ × س` |
| `س/٢` | `س ÷ ٢` |
| `٢س + ٦ = ١٠` | معادلة خطية |
| `٢(س + ٣) = ١٠` | معادلة خطية تحتوي توزيعًا |

حدود الالتباس:

- `٢٣` **عدد واحد**؛ ليس ضرب ٢ × ٣.
- `٢س٣` لا تُعد سلسلة ضرب صحيحة في P0؛ تُطلب صياغة صريحة.
- `س(٢)` ليست ضمن أنماط الضرب الضمني المعتمدة في P0؛ يطلب النظام `س × ٢` إذا كان هذا المقصود.
- `(س + ١)(س + ٢)` تعبير تربيعي خارج P0؛ لا تعني صحة تفسيره أنه مدعوم للتحقق.
- `١/٢س` ملتبسة وتحتاج أقواس.
- `٢−٣س` تُحلّل كطرح حد، أما `−٣س` في بدايته فتحمل سالبًا أحاديًا.
- أي رمز جديد أو سياق متداخل لا يُسمح به صراحة يواجه `unsupported` أو `syntax_error` حسب الحالة، لا محاولة إصلاح صامتة.

### 4.1 المعادلة مقابل التعبير

- **الخطوة** في رحلة الحل P0 تتضمن معادلة واحدة على الأكثر بمتغير `س` وعلامة `=` واحدة.
- التعبير المجرد مثل `٢س + ٣` يمكن للواجهة عرضه أو استخدامه كجزء من معادلة، لكنه **ليس إجابة مكتملة** لسطر يتطلب معادلة.
- سطر به `س=٢=٣` غير صالح بنيويًا في P0؛ لا نحول المساوات المتسلسلة إلى سلسلة تحقق صامتة.
- رفض البنية لا يعني أن الطالب لا يفهم المفهوم الرياضي؛ رسائل الإدخال يجب أن تشرح المطلوب فقط.

## 5. اتجاه الكتابة وعرض المعادلة (RTL) — متطلب صحة لا تجميل

### 5.1 مبادئ الواجهة

1. اتجاه القراءة الأساسي للمحتوى العربي **RTL**.
2. يُعرض كل تعبير رياضي كوحدة **دلالية مستقلة ومعزولة الاتجاه** داخل النص؛ لا يدمج النص الخام في فقرة HTML ويُترك لخوارزمية الاتجاه العامة لتحزر ترتيب الصيغة.
3. **اتجاه الصفحة لا يساوي اتجاه الصيغة.** تستخدم مكونات عرض الرياضيات آلية اتجاه تدعمها الأداة المستخدمة، مثل `dir="rtl"` على عنصر MathML بعد التحقق في المتصفحات المستهدفة.
4. القوسان والإشارة السالبة والأسس والبسط/المقام يجب أن يحافظوا على علاقة رياضية صحيحة مهما تغير اتجاه الواجهة.
5. ترتيب المعادلة **الدلالي المخزن** لا يُعكس أبدًا لمعالجة انعكاس مرئي. علاج العرض يكون في طبقة العرض.
6. الأرقام متعددة الخانات مثل `١٢٣` يجب أن تظهر بترتيب صحيح، لا `٣٢١`.
7. عند نسخ المعادلة أو لصقها تُفضّل صيغة عربية معيارية نصية مستمدة من التمثيل الداخلي؛ **ليس** ترتيب الحروف الظاهر على الشاشة ولا HTML المصيَّر.

### 5.2 حالات مرئية إلزامية

| معرّف | المثال | المطلوب عند العرض |
|---|---|---|
| `RTL-01` | `٢(س + ٣) = ١٠` | الأقواس والمساواة والحدود في مواضع مفهومة ومراجَعة |
| `RTL-02` | `−٣س + ١٢ = ٠` | السالب يتبع المعامل الصحيح ولا يلتصق بالحد الخطأ |
| `RTL-03` | `س = ١/٢` | البسط ١ والمقام ٢ في موضعيهما الصحيحين |
| `RTL-04` | `س = ١٢٣` | ترتيب خانات العدد محفوظ |
| `RTL-05` | «حل المعادلة: `٢س + ٣ = ٧`» | النص المحيط والصيغة المعزولة لا يخلط أحدهما ترتيب الآخر |
| `RTL-06` | تبديل الاتجاه في العنصر الحاوي/التجاوب | معنى المعادلة المرئي لا يتغير مع حجم الشاشة |
| `RTL-07` | نسخ `٢س + ٣ = ٧` ثم لصقه | تُعاد قراءة المعنى الرياضي نفسه |
| `RTL-08` | إدخال `2س + 3` ثم العرض | يظهر `٢س + ٣` دون تبديل ترتيب العمليات |

يجب إجراء الفحص على **المتصفح الفعلي المعتمد للحاسوب والهاتف**، وليس الاكتفاء بصورة لقطة من بيئة واحدة. ويُوثَّق اسم المتصفح وإصداره ونظام التشغيل وحالة كل اختبار.

### 5.3 مراجع العرض

- توثق MathML Core صفة `dir` وإمكان اتجاه المعادلة RTL، لكنها ليست ضمانًا لتطابق كل محرك عرض مع جميع تركيبات الصيغ في بيئات الفريق.
- تُستخدم وثيقة W3C حول الاصطلاح الرياضي العربي **مرجعًا استرشاديًا للاختلافات الإقليمية**، لا وصفة وحيدة مفروضة على كل مناهج الدول العربية.
- الخطوط المختارة للرموز العربية والأرقام والمعادلات يجب أن تُختبر عمليًا. لا نضيف صورًا للمعادلات بديلًا عن التعبير الرياضي القابل للتحديد والتفاعل إلا إذا كان ذلك حلًا مؤقتًا موثقًا يراعي الإتاحة.

## 6. واجهة الإدخال ولوحة المفاتيح العربية

### 6.1 الحد الأدنى P0

يجب أن يستطيع الطالب، بالفأرة أو اللمس أو لوحة المفاتيح، إدخال:

- الأرقام `٠–٩`، والمتغير `س`، والجمع والطرح والمساواة.
- الضرب الصريح، الأقواس، والقسمة على ثابت/الكسر العددي عند دعمه.
- إضافة خطوة، تعديلها، حذفها وفق سياسة الجلسة، والانتقال بين مواضع الإدخال دون إفساد الصيغة.

**ممنوع في P0:** إلزام الطالب بتبديل لوحة الجهاز إلى الإنجليزية ليكتب `x` أو يستخدم دالة إنجليزية بديلة. يمكنه إدخال رمز عبر لوحة افتراضية عربية واضحة.

### 6.2 قواعد التفاعل

- كل زر يحمل اسمًا عربيًا واضحًا واسمًا قابلًا للقراءة لقارئ الشاشة؛ زر `س` يضيف **متغيرًا** لا حقل نص.
- يسهل التمييز بين `−` و`÷` و`×`؛ لا نعتمد على شكل بصري صغير وحده.
- إذا استخدمنا MathLive أو مكتبة مشابهة، يجب تنفيذ **إثبات صلاحية (PoC)** قبل اعتمادها، يشمل الكتابة والتحرير وتحريك المؤشر والنسخ واللصق وRTL والكسور على الهاتف والحاسوب.
- لا يُسمح لمحرك المحرر أن يطبع الرموز إلى LaTeX مع فقد المعلومة عن المتغير العربي أو أن يبدل معنى البسط والمقام.
- صيغة LaTeX — إذا استُخدمت لنقل العرض — **وسيط عرض/تحرير** وليست مرجعًا دلاليًا مستقلًا؛ لا نثق بأي تحويل غير مختبر منها وإليها.
- يستمر الإدخال عند فشل خدمة AI؛ ولا تُفقد خطوات الطالب بسبب خطأ في الشرح أو العرض.

### 6.3 رسائل المعالجة العربية

| الحالة | الرسالة المستهدفة للمستخدم |
|---|---|
| متغير لاتيني في جبر P0 | «في هذا المسار استخدم المتغير س بدلًا من x.» |
| إدخال `جا` | «الدوال المثلثية غير مدعومة في هذا المسار حاليًا.» |
| كسر ملتبس `١/٢س` | «حدد المقصود باستخدام الأقواس، مثل (١/٢)×س أو ١/(٢×س). الصيغة الثانية غير مدعومة هنا.» |
| مقام صفر | «لا يمكن أن يكون مقام الكسر صفرًا. راجع العدد المكتوب.» |
| شكل غير مكتمل | «المعادلة غير مكتملة. تأكد من الأقواس وعلامة المساواة.» |
| خطأ في التحليل | «تعذر فهم هذا الجزء من الصيغة. صححه أو استخدم لوحة الرموز.» |
| صحيحة الصياغة خارج P0 | «هذا النوع من الرياضيات غير مدعوم بعد؛ لم نقيم صحة حلك.» |
| تعذّر إثبات حكم | «فهمنا الصيغة، لكن لا نستطيع التأكد من صحة هذه الخطوة حاليًا.» |
| عطل خدمة | «تعذر التحقق الآن. بقيت خطواتك محفوظة ويمكنك المحاولة مجددًا.» |

هذه **رسائل نموذجية**؛ صياغاتها النهائية تتبع دليل المحتوى العربي وتُختبر مع مستخدمين.

## 7. التطبيع الآمن والمعنى الداخلي

### 7.1 مراحل التعامل مع الإدخال

1. **التقاط الأصل:** يحفظ الإدخال كما أرسله الطالب لأغراض المراجعة وفق سياسة الخصوصية.
2. **فحص المحارف:** تُرفض محارف التحكم/الاتجاه الخفية غير المتوقعة، والمحارف غير المسموحة، قبل التحليل. لا يُبنى معالج بديل عن فحص المحارف.
3. **توحيد محدد:** تحويل أرقام ASCII إلى قيمة عددية مكافئة؛ تحويل `-` إلى مفهوم طرح/سالب؛ توحيد الفراغات المسموح بها. **لا نطبق استبدالات شاملة مجهولة الأثر**.
4. **تحليل رمزي (Lexer):** تمييز عدد، ومتغير `س`، ومشغلات، وقوس، وعلاقة مساواة، ودالة محجوزة غير مدعومة.
5. **تحليل نحوي (Parser):** بناء شجرة منظمة لقواعد P0 وحدها، مع مواضع مصدر (spans) تشير إلى محارف الإدخال الأصلية.
6. **تحليل دلالي:** التأكد من متغير واحد، وصحة المقامات، والخطية، ومجال الصيغ المدعومة.
7. **إنتاج نتيجة قابلة للتتبع:** النص الخام + الشجرة الدلالية + نسخة ملف الاصطلاح + العرض العربي المعاد توليده + سبب الامتناع إن وجد.
8. **تسليم التحقق:** يقرر محرك الرياضيات صحة الانتقال وفق `10-MATH-ENGINE.md`، لا نتيجة Parser وحده.

### 7.2 نموذج دلالي توضيحي غير ملزم بأسماء API

إدخال الطالب: `٢(س + ٣) = ١٠`

```text
Equation(
  Multiply(Integer(2), Add(Variable("س"), Integer(3))),
  Integer(10)
)
```

- هذا **رسم لشجرة معنى**، وليس تمثيل JSON نهائيًا أو عقد API.
- عند عرض النتيجة، يُستخدم ملف الاصطلاح لإنتاج `٢(س + ٣) = ١٠` مع اتجاه وتنسيق معتمدين.
- لا نعتمد على ترتيب النص المصيَّر ولا نجري عملية `reverse()` للنص كحل لـRTL.

### 7.3 محظورات التطبيع والأمان

- **لا** استبدال حرف بحرف على جميع المدخلات دون قواعد نوعية؛ مثل `x → س` أو `sin → جا`.
- **لا** تحليل الجملة العربية الحرة بوصفها شيفرة حسابية قابلة للتنفيذ.
- **لا** تمرير تعبير طالب خام مباشرة إلى `eval` أو `exec` أو `sympify`/`parse_expr` بصيغ غير موثوقة.
- **لا** الاعتماد على `NFKC` شامل دون تدقيق، لأنه قد يغير بعض خصائص التمثيل. نسمح بتطبيع موثق ومحكوم بالمجموعة المدعومة فقط.
- **لا** إدخال علامات اتجاه خفية من النص الخام إلى صيغة التحقق. تستخدم طبقة العرض عزل اتجاه عند الحاجة دون أن تتحول العلامات إلى رموز دلالية مخزنة.
- **لا** تحويل أي تعبير لا يفهمه المحلل إلى «خطأ رياضي» أو «ضعف لدى الطالب».
- تفرض حدود طول الإدخال وعمق الأقواس وحجم الأعداد والوقت والموارد في `10-MATH-ENGINE.md` و`16-SECURITY-PRIVACY.md`.

### 7.4 رموز تحكم تستحق اختبارًا صريحًا

علامات LRM/RLM ومحارف التحكم في الاتجاه (مثل `U+200E` و`U+200F` و`U+202E` و`U+2066–U+2069`) لا تدخل كجزء من لغة الرياضيات P0. عند وجودها في مصدر المستخدم تُرفض أو يُطلب تأكيد إزالة موثَّقة لا تغير المعنى؛ **ولا يُسمح باستعمالها لإخفاء تحويلات أو تبديل معنى السطر**.

## 8. التصنيف الدقيق للحالات؛ لا نتهم الطالب عند غياب الدعم

| نوع الحالة | مثال | نتيجة فحص الإدخال أو الانتقال | ما يقوله النظام |
|---|---|---|---|
| إدخال صالح ومدعوم | `٢س + ٣ = ٧` | تحليل ناجح؛ التحقق لاحقًا | «تم فهم المعادلة» |
| إدخال ناقص | `٢(س + ٣ = ١٠` | `syntax_error` | «أكمل القوس» |
| مقسوم على صفر | `س/٠ = ٢` | `syntax_error` أو خطأ مجال محدد وفق `10-MATH-ENGINE.md` | «لا يمكن القسمة على صفر» |
| موضوع غير مدعوم | `جا(٣٠°) = ١/٢` | `unsupported` | «هذا الموضوع غير مدعوم حاليًا» |
| تعبير يحتاج تفسيرًا | `١/٢س = ٣` | `syntax_error` مع سبب الالتباس | «أضف أقواسًا لتوضيح المقصود» |
| صحيح النحو، فحصه غير محسوم | تحويل يحتاج مجالًا خارج التحقق المحدد | `inconclusive` | «لا يمكن الجزم بصحة هذه الخطوة» |
| انتقال ثابت الصحة | `٢(س + ٣) = ١٠` ← `٢س + ٦ = ١٠` | `verified_valid` | «التحويل صحيح ضمن الشروط المعتمدة» |
| انتقال ثبت خطؤه | `٢(س + ٣) = ١٠` ← `٢س + ٣ = ١٠` | `verified_invalid` | «هذا التحويل غيّر المعادلة؛ راجع التوزيع» |
| فشل خدمة | توقف محرك التحقق | `service_error` | «تعذر التحقق دون فقدان الخطوات» |

**فصل إلزامي:** نتيجة «غير صحيح رياضيًا» لا تثبت وحدها أن سبب الخطأ «عدم فهم خاصية التوزيع». التشخيص التربوي ملك `06-MISCONCEPTIONS.md` و`07-TUTORING-POLICY.md`.

## 10. اختلاف المناهج والأقاليم: ملف اصطلاحات لا نسخ مختلفة من المحرك

نخطط مستقبلًا لإتاحة ملفات اصطلاحات مرتبطة بالمناهج دون تغيير معنى التعبير الرياضي. يحتوي كل ملف لاحقًا على:

- `profile_id` و`version` واسم المنهج المعتمد ومرجع المصطلحات.
- شكل الأرقام والفواصل المعروض والمقبول في الإدخال.
- معجم الدوال والمتغيرات المسموحة ومطابقتها إلى عقد دلالية ثابتة.
- اتجاه الصيغ وقواعد الرموز المتأثرة بالاتجاه.
- قواعد اختصار أسماء الدوال والدرجات والزوايا عند دعمها.
- قاموس رسائل الواجهة ومعايير اختبار مرئية وأمثلة مراجَعة.

**الحد الإلزامي في P0:** ملف واحد مصادق عليه للهاكثون؛ لا نضيف زر «تغيير البلد» دون أن تكون لدينا بيانات اصطلاحات وقواعد اختبار لكل ملف. اختلاف المنطقة ليس مجرد تبديل `dir` أو شكل الأرقام.

## 11. سياسة تخصصات المستقبل خارج P0

### 11.1 الرياضيات الموسعة

- تعتمد `جا` و`جتا` و`ظا` بعد إقرار ملف اصطلاح ونطاق زوايا ومجال رياضي وتحقق مستقل.
- تُضاف متغيرات `ص` و`ع` وعمليات الأسس/الجذور/اللوغاريتمات وفق منهج مراجع ومواصفة جديدة مع اختبارات.
- لا يُسمح بإطلاق أي اسم دالة جديد اعتمادًا على مخرجات LLM وحدها.

### 11.2 الفيزياء

- يمكن استخدام الرموز العربية للكميات إذا نص عليها المنهج المستهدف، أو الرموز الدولية إن كانت المعيار المدرسي المناسب؛ لا نفرض تعريبًا يغير معنى رمز علمي عالمي.
- أسماء الكميات مثل السرعة والتسارع والقوة بالعربية، مع بقاء وحدات النظام الدولي (`m`، `s`، `kg`، `N`) معروفة ومقروءة.
- يحتاج محرك الفيزياء مستقبلًا إلى فحص الأبعاد وتحويل الوحدات، ولا يكفي المحرك الجبري وحده.

### 11.3 الكيمياء

- «الماء» بالعربية، لكن صيغته `H₂O` تظل برموز عناصر دولية صحيحة؛ وينطبق ذلك على `NaCl` وبقية الصيغ.
- المتطلبات المستقبلية تشمل الأعداد السفلية والشحنات والمعادلات الكيميائية واتجاهها وبقاء الرموز والحالات الفيزيائية صحيحة.
- لا يبدل المحلل رمز عنصر لاتينيًا بحرف عربي مشابه الشكل.

### 11.4 البرمجة

- نصوص التعليم والشرح بالعربية؛ نص الشيفرة في اتجاه LTR وبأحرف وأسماء المكتبات/الوظائف وفق اللغة الأصلية مثل `Python`, `if`, `return`.
- لا تعريب للكلمات المحجوزة ضمن ملفات المصدر، ولا إعادة ترتيب للأسطر بسبب RTL.
- تعرض مقاطع الكود في وحدات مستقلة الاتجاه، حتى داخل صفحة عربية.

## 12. الإتاحة وقابلية الاستخدام

- لا يُستعاض عن المعادلة الدلالية بصورة ثابتة وحدها؛ يجب أن تكون قابلة للنسخ/القراءة أو لها بديل نصي عربي مفهوم.
- يُستهدف تمكين الطالب من إكمال رحلة الإدخال باستخدام لوحة المفاتيح دون فأرة، وفق ما تسمح به الأداة المختارة.
- يقدّم كل رمز اسمًا منطوقًا عربيًا مناسبًا: `س` ← «المتغير س»، `×` ← «ضرب»، الكسر ← «واحد على اثنين» أو وصفًا محسومًا في المرجع.
- تتضمن اختبارات الجودة قارئ شاشة واحدًا على الأقل، مع تسجيل محدوديات أداة الرياضيات إن وجدت بدل ادعاء إتاحة كاملة غير مختبرة.
- يجب ألا يكون اللون وحده دليلًا على صحة/خطأ التحويل؛ توجد أيقونة ورسالة وحالة نصية.
- يحافظ التكبير والتجاوب على إمكانية فهم الكسر والأقواس والأرقام، دون قص طرف معادلة في الهاتف.

## 13. حالات قبول إلزامية لوكلاء الواجهة والمحرك والاختبارات

> **قاعدة تنفيذ:** الأسماء `AN-*` معرّفات ثابتة للحالات المرجعية، وليست أسماء API. عند تعديل أي حالة، يجب تحديث مجموعة الاختبارات المرجعية وإعلان أثر القرار.

| المعرّف | الإدخال | السلوك المتوقع P0 | التخصص |
|---|---|---|---|

| `AN-016` | `٢(س + ٣ = ١٠` | `syntax_error` مع موضع القوس الناقص | تركيب |
| `AN-017` | `س=٢=٣` | `syntax_error` لمساواة متسلسلة غير مدعومة | تركيب |
| `AN-018` | `x + ٣ = ٧` | `unsupported` لمتغير غير مدعوم مع توضيح استخدام س؛ لا تحويل صامت | متغيرات |
| `AN-019` | `ص + ٣ = ٧` | `unsupported` لمتغير عربي غير مدعوم حاليًا | متغيرات |
| `AN-020` | `جا(٣٠°) = ١/٢` | `unsupported` للدالة المثلثية؛ لا حكم صحة | حدود النطاق |
| `AN-021` | `س² + ١ = ٠` | `unsupported` للأسس والمعادلات غير الخطية | حدود النطاق |
| `AN-022` | `١/س = ٢` | `unsupported` للمقام المتغير؛ حفظ شرط المجال | حدود النطاق |
| `AN-023` | `٣٫٥س = ٧` | `unsupported` للأعداد العشرية في P0، لا تغيير صامت إلى ٣٥ | تنسيق العدد |
| `AN-024` | `١،٥س = ٣` | لا تُعامل الفاصلة العربية `،` كنقطة عشرية | تنسيق العدد |
| `AN-025` | `٢(س + ٣) = ١٠` ← `٢س + ٦ = ١٠` | `verified_valid` مع دليل ملائم | تحقق |
| `AN-026` | `٢(س + ٣) = ١٠` ← `٢س + ٣ = ١٠` | `verified_invalid`؛ تشخيص تربوي احتمالي فقط | تحقق |
| `AN-027` | `٢(س + ٣) = ١٠` ← `س + ٣ = ٥` | `verified_valid`؛ قبول حل صحيح بديل | تحقق |
| `AN-028` | `س = ١٢٣` | ترتيب الرقم ١٢٣ صحيح بصريًا على الحاسوب والهاتف | عرض |
| `AN-029` | نسخ ولصق `٢س + ٣ = ٧` | النص المنسوخ يعاد تحليله إلى المعنى نفسه | حافظة |
| `AN-030` | إدخال يتضمن `U+202E` أو محرف اتجاه خفي | رفض/تحقق آمن مع رسالة؛ لا تغيير خفي للمعنى | أمن/RTL |
| `AN-031` | `سَ = ٢` | لا يُختزل التشكيل خفية إلى س؛ رسالة مراجعة اصطلاح | محارف |
| `AN-032` | `س = ٢` مع نص شرح محيط RTL | المعادلة معزولة بصريًا ولا تتغير قيمتها أو ترتيبها | RTL |
| `AN-033` | تعديل خطوة سبق التحقق منها | إعادة توليد العرض والحكم للخطوات التابعة دون أحكام قديمة | تكامل |
| `AN-034` | إدخال غير مدعوم | لا يظهر كخطأ مفاهيمي ولا يدخل ملخص إتقان الطالب بوصفه إخفاقًا | تعليم |
| `AN-035` | سقوط محرك AI أثناء حل صحيح | تبقى المعادلة والحكم الرياضي وآخر خطوة محفوظة | مرونة |

### 13.1 مصفوفة متصفحات مبدئية

- **حاسوب:** Chrome حديث + Firefox حديث على نظام يُعتمده الفريق.
- **هاتف حقيقي:** Chrome على Android أو Safari على iOS، مع اختبار اللمس والتحرير والأقواس والكسر.
- يجب توثيق الأجهزة/الإصدارات الفعلية عند الاختبار؛ الأمثلة أعلاه **مصفوفة مستهدفة لا تقرير نجاح**.
- لا تُعد `AN-028` و`RTL-*` ناجحة اعتمادًا على مقارنة نصية فقط؛ تحتاج فحصًا مرئيًا ومعنويًا، ويفضل لقطة/تسجيلًا مع حالة الإدخال نفسها.

### 13.2 معيار عدم اعتماد التطبيق

أي حالة من التالي **مانع إطلاق**:

1. `٢(س + ٣)` تُحلّل كعملية مغايرة للضرب في المجموع.
2. `١/٢` ينقلب فيه البسط والمقام بسبب RTL أو النسخ أو التصيير.
3. قبول تحويل غير صحيح بوصفه صحيحًا أو العكس بثقة، بسبب خطأ تطبيع/اتجاه.
4. قبول إدخال غير مفهوم على أنه صحيح دون توضيح، أو اتهام الطالب بخطأ عند `unsupported` / `inconclusive`.
5. تنفيذ بيانات الطالب غير الموثوقة شيفرةً أو تسربها إلى جلسة مستخدم آخر.

## 14. واجبات الوكلاء، وآلية التغيير، ومسؤولية الاعتماد

### 14.1 واجبات كل فريق

| الجودة | اختبارات `AN-*` و`RTL-*`، وإثبات عدم تغيّر معنى الصيغة عبر الإدخال/الحفظ/العرض/النسخ |
| مختص المادة | اعتماد قاموس الجبر، وتأكيد الصيغ التربوية والاصطلاح الأول |

### 14.2 قاعدة التغيير

أي تعديل في رموز الإدخال المقبولة أو طريقة العرض أو تفسير الضرب الضمني أو ملف الاصطلاح يوجب:

1. كتابة طلب تغيير يشرح السبب والحالة التعليمية المتأثرة.
2. مراجعة مختص المادة إن كان الاصطلاح علميًا أو منهجيًا.
3. تحديث `04-ARABIC-NOTATION.md` و`14-GOLDEN-DATASET.md` و`15-TEST-AND-ACCEPTANCE.md` والاختبارات المرافقة.
4. فحص أثر القرار على `10-MATH-ENGINE.md` والعقود في `12-API-CONTRACT.yaml` إذا تغير السلوك أو البيانات.
5. إعادة تشغيل حالات القبول المستهدفة وتوثيق النتائج دون اختلاق نسبة نجاح.

**ممنوع** تعديل `ARABIC-NOTATION` من وكيل واحد لإسكات اختبار فاشل دون إشعار قائد التكامل ومالك القرار.
