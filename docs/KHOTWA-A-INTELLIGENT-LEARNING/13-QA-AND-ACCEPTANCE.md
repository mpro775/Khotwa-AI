# 13 — خطة الفحوص وبوابات القبول A1–A8

## سياسة الاختبارات

- قبل كل مرحلة: فحص diff؛ اختبارات وحدة للتصميم المضاف؛ contract/schema/typecheck/lint؛ ثم اختبار اندماج مستهدف بالحد الأدنى اللازم. لا تمسح قاعدة مستخدمين، لا تستبدل fixtures المقبولة القديمة ولا تعيد كتابة Golden.
- الاختبارات ببيانات اصطناعية وحسابين مستقلين على الأقل، وPostgreSQL مملوكة للاختبار عند الحاجة. لا تزعم نجاح E2E إن لم يجر فعليًا.
- `npm run contracts:check`, `npm run typecheck`, `npm run lint`, `npm run build` تُشغل عند جاهزية البيئة وبالأثر المقبول؛ يمكن تشغيل المستهدف أولًا لتجنب اختبارات حمل أو Gemini live بلا تفويض.
- لا تشغيل LLM خارجي ولا Runner ولا نشر ولا migrations إنتاجية. اختبار deadline/spacing بحقن clock أو fake timers، لا انتظار أيام فعلية.

## Golden الجديد

أضف **حزمة حالات A** مستقلة عن `docs/14-GOLDEN-DATASET.cases.json`، في مجلد يختاره الوكيل مثل `qa/fixtures/intelligent-learning-a/`. يجب أن تحتوي حالات: جبر بخطأ توزيع وحل بديل صحيح، فيزياء قيمة ووحدة، غياب بنك جديد، AI off، دعم H4، mapping دورة، تواريخ 1/3/7 أيام اصطناعية، كلام الطالب بثقة عالية مع جواب خاطئ. اختبارات التحكيم تتوقع verdict من المحرك، ولا تضبط مخرجات Golden القديمة حتى تمر.

## تجربة تكامل عمودية واحدة واجبة

حساب طالب اصطناعي يبدأ جبر `ALG-L04`: اختبار→A1 يختار probe أو مثال→A3 يختبر السبب المحتمل→A6 يخفف الدعم→سؤالان جديدان مستقلان مع الحكم الحقيقي→A2 يبيّن شهادة مستقلة محدودة→A5 يضيف موعد مراجعة→وقت اختباري مؤجل يخلق سؤال جديدًا→A8 يقارن الهدف مع الأدلة→A7 offline يقدم سؤالًا سقراطيًا في التدريب. يسجل اختبار تكامل آخر انتقال physics unit ورفض Python runner.

## معايير الخروج النهائية

- `PASS` التقني فقط عندما تنجح الاختبارات المذكورة في بيئة مسجلة مع command/output وrevision.
- `PARTIAL` عندما تعمل الطبقة التقنية لكن المحتوى أو المراجعة البشرية أو Runner غير جاهز؛ لا تلوّن `PARTIAL` كجاهز إنتاجيًا.
- `BLOCKED` عند تغيير عقد/تعليم لا يمكن إتمامه دون صاحب قرار؛ استمر في مهام أخرى مستقلة، وثّق blocker بوضوح.
- لا تعلن أثرًا تعليميًا (زيادة الفهم أو الاحتفاظ) دون بيانات تجربة ومقارنة مناسبة؛ هذا البرنامج يثبت **صحة السلوك والتكامل** أولًا.
