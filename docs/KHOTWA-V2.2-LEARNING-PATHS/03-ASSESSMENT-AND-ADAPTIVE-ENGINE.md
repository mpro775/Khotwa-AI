# V2.2 / TASK-LP-03 — الاختبار التشخيصي والتوصية والتعلم العلاجي

## النتيجة المطلوبة
يختار الطالب «اختبر مستواك في الجبر» أو «تعلّم الدرس»، ويؤدي الأول إلى: **تقييم قصير مستقل → أدلة مهارات → درس مُوصى به → شرح وتدريب → سؤال نقل مستقل → تحديث التقدم**.

## 1. الاختبار التشخيصي (Assessment)
- أنشئ `assessment_session` أو استعمل كيان جلسة/حلقة قائمًا مع نوع `diagnostic_pretest | lesson_check | post_remediation`، ونسخة قائمة أسئلة مثبتة عند البدء. يحدد السيرفر الموضوع والمهارات؛ الواجهة لا ترسل أحكامًا.
- اختبر أولًا الجبر بمجموع **8–12 سؤالًا** من مسائل `published/reviewed`، موزعة على مهارات المسار. لا تُنشئ أسئلة تعتمد على بيانات لم تراجع، ولا تستخدم مشكلة الكسور المحجوبة. إذا لا يكفي البنك، اعرض نقص التغطية وسجّل التقييم الجزئي بدل اختلاق سؤال.
- لا تُظهر تلميحات أو الحل النهائي في نمط **القياس المستقل**. إذا طلب الطالب المساعدة فحوّل المحاولة إلى وضع ممارسة، وسجّل خروجه من القياس قبل إرسال تلميح؛ النتيجة لا تعُد دليلًا مستقلًا.
- خزّن `expectedRevision` و`Idempotency-Key` وتوقيت/نسخة محاولة الطالب في مسارات الحفظ والتحقق، ولا تقبل نتيجة متأخرة بعد تعديل الإجابة. احمِ ملكية المستخدم.
- لكل إجابة خزّن: `subject`, `skillCode`, `problemRevisionId`, `mathVerdict`, `diagnosisCandidate?`, `supportLevel`, `independence`, `evidenceSource`, `timestamp/version`. لا تنقل حقل الإجابة المرجعية المخفي للعميل.

## 2. تجميع الأدلة
- أعد استخدام `skill_evidence`, `progress.ts`, `subject_attempts` بدل إنشاء جدول «درجة إتقان» منفصل يناقض التقدم القديم.
- اجمع عدد المحاولات المستقلة الصحيحة والخاطئة لكل مهارة ودرجة موثوقية التشخيص. اختبارات قليلة تعني **أدلة غير كافية**، لا 0% ذكاء أو رسوبًا دائمًا.
- حد أدنى مقترح للترقية إلى `independent_evidence`: **نجاح مستقل في سؤالين مختلفين على الأقل** للمهارة، بشرط تغطية السؤالين وتماثل مستوى الصعوبة. هذا معيار ابتدائي قابل للضبط والمراجعة، وليس وعدًا بحثيًا بالإتقان؛ وثّقه قبل استعمال كلمة «متقن».
- الخطوات الصحيحة مع H1–H4 تسجل تقدّمًا بالمساعدة، ولا تكفي وحدها لمستوى استقلال.
- بعد فشل الخدمة أو `inconclusive/unsupported` لا تعامل النتيجة كإجابة خاطئة.

## 3. محرك التوصيات الخفيف (deterministic first)
اعتمد ترتيبًا بسيطًا ثابتًا، بلا ML model إضافي:
1. حلّل المهارات التي قاسها الاختبار وأعد حالة evidence لكل مهارة.
2. استبعد أي مهارة/درس غير منشور أو غير مدعوم أو رابطُه لم يُراجع.
3. اعطِ الأولوية لمهارة عليها **دليل متكرر مستقل** على الحاجة للمراجعة، ثم لمقدماتها غير المكتملة إن كانت تمنع الدرس.
4. إن لم يوجد دليل كافٍ، اقترح درس تمهيد أو سؤال تثبيت قصير، ولا تختلق ضعفًا.
5. أعِد توصية واحدة رئيسية مع سبب قابل للتفسير ورابط الدرس والمهارة، وخيارات متابعة بديلة.
6. حافظ على اختيار الطالب الحر: لا تحبسه داخل مسار «ضعف» ولا تمنع فتح الدروس الأخرى.

شكل الاستجابة المقترح (يُكيَّف مع OpenAPI القائم):
```json
{
  "recommendedLessonId": "lesson-id",
  "targetSkillCode": "EXISTING_SKILL_CODE",
  "reasonCode": "repeated_independent_error",
  "reasonAr": "قد تفيدك مراجعة توزيع الأقواس بناءً على الحلول السابقة.",
  "confidence": "tentative",
  "evidenceCount": 2,
  "nextAction": "study_lesson"
}
```
لا تعرض معرفًا خاصًا أو نتيجة نفسية أو أحكامًا قاطعة. تظل `confidence` مرتبطة بالأدلة الفعلية لا بمخرج Gemini.

## 4. العلاج ثم إعادة الاختبار
- بعد فتح الدرس: سجل `lesson_started/lesson_viewed` دون اعتبار العرض فهمًا.
- تدريب موجّه من 2–3 أسئلة متاحة ومراجعة مرتبطة بالمهارة؛ التلميحات H0–H4 وGemini/Fallback عبر السياسات القائمة.
- اختر **سؤال نقل/تثبيت مختلفًا** عن سؤال التقييم السابق وعن المثال المحلول؛ لا تستخدم نفس problem revision في post-test، ولا تعرض الحل أو التلميح خلال قياس الاستقلال.
- حدِّث progress فقط من محاولات مرجعية حقيقية؛ إن نجح بمساعدة فقط فاعرض «تتقدم بمساعدة» لا «أتقنت».
- احتفظ بسجل مسار التوصية (ruleVersion, lessonRevisionId, evidence IDs) لإعادة إنتاج سببها بعد تحديث المحتوى.

## 5. الـAPI والـDB
- مدّد واجهات `/assessments/start`, `/assessments/:id/answer`, `/assessments/:id/summary`, `/recommendations/next`, `/lessons/:id/progress` أو مسارات مكافئة قانونية، **لا تنشئ API ثانٍ لوظائف موجودة**.
- تحقق أن student/account/guest يملك التقييم؛ المعلم لا يرى بيانات طالب حقيقي إلا بصلاحيات صريحة ضمن منتج لاحق.
- أضف فهارس صغيرة للملكية + (skill/version/date) حسب الحاجة، مع migrations قابلة للمراجعة؛ لا migrations في الإنتاج تلقائيًا.
- لا تسجّل نص Gemini الخام أو معرّفات حساسة في telemetry دون ضرورة.

## 6. أمثلة اختبارات دقيقة
1. أربع محاولات فيها خطأ توزيع متكرر → درس توزيع الأقواس، مع بيان الأدلة دون الجزم بسبب الخطأ.
2. خطأ واحد فقط + نجاح مستقل → توصية متحفظة أو سؤال تثبيت.
3. نجاح بمساعدة H2 → `practice_with_support` لا `independent_evidence`.
4. عدم توفر محرك SymPy → `service_error` لا «خطأ الطالب».
5. طلب مساعدة أثناء post-test → خروج صريح من القياس، وعدم تسجيل النتيجة كدليل مستقل.
6. تكرار POST بنفس idempotency key → لا سؤال مكرر ولا دليل مزدوج.
7. محاولتان متزامنتان مع مراجعة قديمة → رفض stale result.

**التسليم:** قرار توصية قابل للتفسير، تقييم قصير حقيقي، علاج وربط دراسة، وإعادة قياس مستقلة مع اختبارات وحدات وتكامل مستهدفة.
