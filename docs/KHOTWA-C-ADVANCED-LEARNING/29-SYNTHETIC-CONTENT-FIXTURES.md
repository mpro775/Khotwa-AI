# 29 — محتوى اصطناعي يُستخدم فقط للاختبار C1–C5

> **ليست دروسًا معتمدة للنشر.** كل fixture يتطلب validation علمي/تربوي/accessibility قبل إدخاله في بنك حقيقي. لا تتحايل على `mappingPending` ولا تستخدمه دليل إتقان.

## C1 — ثلاث مشكلات
| id | المادة/الهدف | موقف واقعي | إثبات قابل للتحقق وتحديات |

### قواعد نشر fixtures
- خاصية `reviewStatus=TEST_ONLY` أو وسم مكافئ في fixtures/log؛ لا تكتب `approvedBy: teacher` اصطناعيًا.
- `C1-PHY-TRAVEL-01` مثال حساب مرجعي للمراجعة؛ **لا تجبر B2 محاكاة توقف** إذا نموذج B2 لا يدعم قطاعات متعددة؛ اخفِ المحاكاة أو مثّل جزأين مستقلين مع توضيح.
- أجوبة/استراتيجيات المرجع في author/private fixture؛ public payload يقتصر على scenario/criteria/allowed aids.
- استخدم Bank مستقل لـpre/post/transfer؛ لا تختبر نفس معطيات الأمثلة بعد تعرضها كتقييم مستقل.

## C2 — ثلاثة مشاريع micro
1. `C2-MATH-TARIFF-MODEL`: جدول مقارنة تسعير وتقرير/رسم مع الافتراضات ومراجعة حلين؛ milestones goal→model→check→revise→present.
2. `C2-PHY-MOTION-REPORT`: تقرير بسيط يفسر جدول حركة خطية وناتج محاكاة B2 إن كانت متاحة اصطناعيًا، مع مقاييس ووحدات وسرد. لا يستخدم قوى أو احتكاك.
3. `C2-CODE-EXPENSE-PLANNER`: نموذج حساب ميزانية باستخدام شروط وتكرار، كود نصي/Parsons وedge-case traces فقط؛ Gate-R مغلق فلا توجد اختبارات تشغيل.

## C3 — variants
لكل fixture تمثيل نص عربي منضبط، جدول بيانات مع رؤوس، رسم وصفه نصي وبديل للقراء، وتعليمات keyboard للتغيير؛ كل variant يذكر هل هو **تعلم** أو **تقييم** ودرجة كشف الحل. لا نخلط تلميحًا مع خيار وصول.

## C5 — dataset اختبار مصغر
- طالب S1: تدريب C1 مع H2 ثم نجاح بمساعدة؛ post مستقل على مسألة جديدة صح؛ delayed بعد7 أيام صح.
- طالب S2: مشروع مكتمل بعد feedback بشرية؛ لا تقييم مستقل؛ analytics = project completed وmastery غير مقاس.
- طالب S3: تشغيل B2 تعطل؛ `technical_abstain`; لا يدخل حساب `failure` للطالب.
- event replay لنفس ID 10 مرات = نفس المقامات، وتقارير طالب آخر 404.

## بيانات مصدرية يجب عدم العبث بها
لا تغيّر بنك الجبر/الفيزياء/البرمجة السابق ولا Golden المرجعي لإرضاء الحالات الجديدة. اختبر fixtures الجديدة من ملفات اختبار خاصة بالحزمة حتى يوقع مراجِع المحتوى.
